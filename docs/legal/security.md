# 安全与贡献

本页说明 Linxira 的签名信任链、安全更新能覆盖到哪里、发现问题后如何私密报告，以及代码、文档、翻译和技能是怎么合进项目的。官方安全中心 <https://linxira-os.github.io/zh/security/> 是权威版本，本页是 Wiki 内的入口与解释。

## 安全模型

| 机制 | 作用 | 边界 |
|---|---|---|
| `[linxira]` 包与仓库数据库签名 | pacman 在安装时校验，确认包来自 Linxira 且未被篡改 | 只证明来源与完整性，不证明代码没有漏洞 |
| Ed25519 密钥分离 | 主密钥（Certify）离线保管，日常签名只用签名子密钥 | 密钥轮换与保管由维护者离线完成，用户侧只信任随包分发的公钥 |
| keyring 分发公钥 | 安装 Linxira 或添加 `[linxira]` 时，pacman 自动导入并信任签名密钥，无需手动操作 | 公钥材料只通过官方发布公告与仓库元数据提供，网站不陈列指纹 |
| 滚动安全更新 | Arch 的安全补丁发布后随下一次 `pacman -Syu` 进入系统，没有额外的冻结周期 | 修复速度取决于上游；本地改动仍需你自己跟进 |
| 双内核 | `linux` 与 `linux-lts` 并存，单一内核更新出问题时可回退 | 不是自动回滚：需要你从引导菜单选择另一个内核 |
| 更新前快照 | 更新事务前创建 Timeshift 快照，可从 GRUB 菜单回到更新前的系统 | 快照在本地磁盘；磁盘本身损坏时快照一起丢失 |
| 无遥测 | 不收集使用数据 | 只有你显式运行诊断收集/上传命令时，诊断包才会按你选择的渠道离开本机 |

## 签名与信任链

全部 Linxira 软件包与仓库数据库由项目自有密钥签发，pacman 安装时验证。密钥算法为 Ed25519：主密钥只用于管理子密钥并保持离线，日常的包与仓库签名由签名子密钥完成。

签名公钥随系统 keyring 包分发。安装 Linxira 或添加 `[linxira]` 仓库时，pacman 会自动导入并信任该密钥，不需要手工 `pacman-key` 操作。公钥材料仅通过官方发布公告与仓库元数据提供，网站不陈列指纹。

!!! note "签名解决的是来源问题"
    签名验证回答“这个包是不是 Linxira 构建的、有没有被中间人改过”，不回答“这段代码有没有漏洞”。后者靠上游修复与你的更新节奏。

## 安全更新

- **滚动更新**：内核、glibc、浏览器等使用 Arch 自己的构建，上游安全通告发布后随下一次 `pacman -Syu` 到达，不经过发行版冻结期。可用 `arch-audit` 检查本机已知问题，上游通告见 <https://security.archlinux.org/>。
- **双内核兜底**：`linux` + `linux-lts` 并存。内核更新导致无法启动时，从引导菜单选择另一个内核进入系统。
- **更新前快照**：`linxira-update` 在事务前创建 Timeshift 快照，快照自动进入 GRUB 菜单，可先以只读方式启动确认，再决定回滚。快照的启用与策略由 `linxira-config` 的 `timeshift` 子命令管理。
- **签名强制**：仓库数据库与软件包签名都在 pacman 侧校验，未签名或签名不符的包不会被接受。

!!! warning "先备份，再更新"
    快照不是备份。重要数据要单独备份到另一块磁盘或远端；不要在没有退路的情况下对唯一设备做大版本升级或分区操作。

## 这个模型不覆盖什么

- **AUR**：AUR 不是仓库而是用户提交的构建脚本集合，包在你的机器上编译，没有签名背书。它默认未启用，也没有预装 AUR 助手。要用就自己读完整 PKGBUILD 与 `.install` 文件，并自行承担后果。
- **第三方与专有软件**：专有驱动、闭源应用有自己的更新与安全渠道，本项目无法替它们打补丁。
- **你自己改过的配置**：本地修改过的配置文件不会随包更新自动修复，升级时的 `.pacnew` 需要你手工合并。

## 报告漏洞

请**不要**在公开 Issue、讨论区或社交平台张贴漏洞细节。正确路径是：

1. 打开受影响组件所在的仓库，例如 <https://github.com/Linxira-OS>，进入 **Security** 标签。
2. 选择 **Report a vulnerability**，通过 GitHub Security Advisory 私密提交；内容仅仓库维护者可见。
3. 报告里写清：受影响的组件与版本、影响范围（能否提权、能否远程触发、影响哪些数据）、最小复现步骤，以及如果你有修复思路，附上建议的修复方向。
4. 在修复发布前保持私密；维护者会与你协调公开披露的时间。

!!! warning "响应是尽力而为"
    项目由个人/小团队维护，没有 24/7 安全响应团队，也没有承诺的响应时限。除某个仓库明确说明外，项目不提供金钱奖励的漏洞赏金。能在本地复现、范围清晰的报告会更快得到处理。

## 贡献模型

- **统一走公开仓库与 Pull Request**：代码、文档、翻译、技能都提交到对应的公开仓库，经审阅后合并。CI 会先跑边界检查与构建，通不过的改动不会被合并。
- **审阅是必需的**：任何改动都要经过维护者审阅；没有“先合再改”的通道，安全相关改动同样如此。
- **AI 辅助贡献**：与其他贡献走同一条公开提交与审阅流程，提交者对所提交内容的正确性和许可合规负责。
- **安全修复先私下协调**：漏洞在修复与发布准备完成之前不走公开 PR，避免在用户拿到补丁前暴露细节。
- **许可见**：[许可与法律](license.md) 说明代码与文档各自的许可；提交即表示你同意按对应仓库的许可发布你的贡献。
